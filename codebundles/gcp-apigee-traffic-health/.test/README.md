# gcp-apigee-traffic-health — Test Infrastructure

## Start here: the tiers that need no cloud and no credentials

These are the tiers that gate a PR, they cost nothing to run, and they are the
ones to run first.

```bash
./validate-all-tests.sh    # both tiers below
./offline/run.sh           # 130 assertions: check logic + static wiring
./render/run.sh            # 19 assertions: templates through runwhen-local's jinja2
```

or `task run-mock-tests` / `task test-offline` / `task test-render`.

- **`offline/`** runs every script against canned data and asserts on what it
  reports, then statically checks the generation rule, both templates and the
  runbook wiring.
- **`render/`** renders the SLX and taskset templates through the same jinja2
  configuration runwhen-local uses. It needs `jinja2` and `pyyaml`; without them
  it **skips loudly** rather than reporting a success it did not earn.

Everything below the *Live flow* heading needs a GCP project and will spend
money.

## Two kinds of fixture, and why

| Directory | Contents | What a mistake here would hide |
|---|---|---|
| `offline/fixtures/` | Apigee Management API responses, generated by `offline/fixtures.sh` from the Apigee v1 **discovery document** | a response-shape defect — reading `.targetServers[].name` off an endpoint that returns a bare array of strings, which made the target check evaluate nothing while rendering as passed |
| `mock/` | Cloud Monitoring aggregates in the bundle's own `MOCK_DATA_FILE` format | nothing: these are the bundle's own intermediate shape, so there is no API contract to get wrong. They exercise threshold and aggregation logic |

The provenance rule for `offline/fixtures/` is absolute: take the shape from the
discovery document or from a recorded real response, never from what the code
expects to see. If a fixture is ever "fixed" to make a test pass, that is the bug
reproducing itself. Read the header of `offline/fixtures.sh` before changing one.

### Mock scenarios

| Scenario | What it seeds | Expected findings |
|---|---|---|
| `healthy` | every proxy and target under threshold, no anomalies | 0 across every check |
| `high_error` | one proxy (`payments-api`) at ~10.5% error/fault rate | 1 error-rate issue |
| `latency_target` | one proxy (`orders-api`) at p95 900ms; one target (`backend-payments`) at p95 800ms | 1 latency + 1 target issue |
| `multi_offender` | **three** proxies over the error threshold, two over latency, two degraded targets, one environment collapsed and one spiked | 1 error + 1 latency + 2 target + 2 throughput — one per *failure mode*, never one per resource |

`multi_offender` exists specifically so the aggregation contract is testable. With
one offender per scenario, a regression that emitted one issue per proxy would
still produce a count of 1 and pass.

## Live flow

Terraform here provisions **no cloud resources**. An Apigee X org is
one-per-project and is owned by the `gcp-apigee-environment-health` sibling's
bootstrap; the signals this bundle reads are Cloud Monitoring time series that
require live traffic through a runtime instance on a private IP. Terraform can
manufacture neither.

What `terraform/` does instead is publish, as outputs, what a discovery run is
expected to produce — the gated resource type, the expected SLX count, and the
expected `resourcePath` — so a run has something machine-readable to be checked
against.

```bash
cd .test
task build-infra           # resolves credentials, then terraform init/plan/apply
task default               # offline tiers, then discovery + generation-rule validation
task clean                 # destroys only what this state owns
```

`task default` reaches discovery deliberately. This bundle's generation rule
gates on `gcp_apigee_organizations`, and only an actual discovery run confirms
the qualifier and the org anchoring end to end — a green run that stopped at the
mock tier would say nothing about the rule.

Credentials come from `terraform/tf.secret` via `load-credentials.sh`, the shared
contract all four Apigee bundles use. It accepts either spelling of the
organization (`APIGEE_ORG` bare, `TF_VAR_org_id` prefixed), strips the
`organizations/` prefix before it reaches a REST path, and warns when an ambient
environment variable disagrees with the file.

`run-rwl-discovery` pins the RunWhen Local image and probes it before running:
on an image whose GCP resource-type registry predates Apigee support, discovery
exits 0 with **zero SLXs**, which reads as "the rule matched nothing" when it is
really an image problem.

## Known gap

There is no path from real Apigee traffic → Cloud Monitoring time series →
finding. Nothing in the collection generates Apigee traffic, and the blocker is
structural: an Apigee X runtime instance is reachable only on a private IP inside
the peered VPC, so producing traffic needs a client inside that network. Until
that exists, the threshold logic is well covered and the ingestion path is not
covered at all.

## Requirements

- `jq` and `bash` for the offline tier
- `python3` with `jinja2` + `pyyaml` for the render tier (skipped loudly without)
- `task` (go-task) for the Taskfile targets
- `curl`, `yq`, `ajv`, `jq` for `validate-generation-rules`
- `docker`, `gcloud`, `terraform` and a service account with
  `roles/monitoring.viewer` + `roles/apigee.readOnlyAdmin` for the live flow
